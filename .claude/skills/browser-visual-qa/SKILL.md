# Визуальная проверка в браузере

Проверка глазами игрока: игру открывают в Chromium, играют мышью (росчерки ножа,
перетаскивание, удержание), снимают каждый экран на 1280×720 и 1440×900 и сверяют
с `production/qa/visual-qa-checklist.md`. Вызов функций `session` — только чтобы
**прочитать** состояние или перемотать время, не чтобы нажать кнопку за игрока.

## Когда запускать

- после каждой большой правки: HUD/панели, телефон, модели/свет, механика станции;
- перед каждой сборкой для владельца (`npx vite build`, `VITE_NEUTRAL=1 npx vite build`);
- после исправления бага с категорией UI или Visual — как подтверждение.

## Подготовка

```bash
cd /home/user/Sites && npm test && npx vite build
npx vite preview --port 4174 --strictPort &      # свой порт; чужой 4173 не трогать
export PW=/opt/node-tools/node_modules/playwright/index.mjs
```

Запуск браузера — только так (без GPU в контейнере):

```js
const { chromium } = await import(process.env.PW ?? 'playwright');
const browser = await chromium.launch({ args: ['--use-angle=swiftshader', '--enable-unsafe-swiftshader', '--ignore-gpu-blocklist'] });
```

Игра отдаёт `window.__sueta = { session, mode, sv, view, app, save }` и без `?dev`;
панель `#dev` появляется только с `?dev`. Основной прогон — **без `?dev`**, с `?seed=3`.

## Помощники мыши (готовые — в `scripts/campaign-e2e.mjs`)

```js
const U = 0.042; // метров на кубик доски (BOARD_UNIT)
const local = (x, z) => page.evaluate(([x, z]) => { const s = window.__sueta.session;
  return s.panel ? window.__sueta.view.localToScreen(s.panel, x, z) : null; }, [x, z]);
// Росчерк: нажал — провёл — отпустил (единицы доски; сверху вниз — полоски, слева направо — кубики)
async function stroke(x0, z0, x1, z1, steps = 8) {
  const a = await local(x0 * U, z0 * U), b = await local(x1 * U, z1 * U);
  await page.mouse.move(a.x, a.y); await page.mouse.down();
  await page.mouse.move(b.x, b.y, { steps }); await page.mouse.up();
  await waitFor(() => !window.__sueta.session.action);
}
// Перетаскивание по точкам в локальных метрах станции (миска, поднос, губка, тряпка)
async function dragTo(points, steps = 4) {
  let p = await local(...points[0]); await page.mouse.move(p.x, p.y); await page.mouse.down();
  for (const pt of points.slice(1)) { p = await local(...pt); await page.mouse.move(p.x, p.y, { steps }); }
  await page.mouse.up();
}
async function clickCanvasAt(x, z) { const p = await local(x, z); await page.mouse.click(p.x, p.y); }
```

Кнопки нажимать по команде, а не по тексту или классу (интерфейс переделывается):
`button[data-act="boardSelect"][data-args*='"olivier:carrot"']`. Станции — подписью
`.st-label` или кликом мышью по `view.stationScreen(id)`; `session.goTo` — только как
обход, и каждый обход перечисляется в отчёте.

## Процедура

1. **Ошибки консоли** — до первого `goto`:
   `page.on('console', m => m.type() === 'error' && logs.push(m.text()))` и `page.on('pageerror', …)`.
2. **Обычный режим** — открыть `url?seed=3`, очистить `localStorage`, открыть снова.
   Провал, если виден `#dev`, есть `#dev-stats` или на странице текст `DEV`/`FPS`.
3. **Два разрешения** — весь сценарий дважды: `1280 720` и `1440 900`
   (`node scripts/campaign-e2e.mjs http://localhost:4174/ 1280 720 d1`, затем `1440 900`).
4. **Сценарий дня 1 мышью**: меню → интро → кухня → Esc (пауза) → Q (рецепты) →
   клик по полу → плита (две кастрюли) → телефон (каждая вкладка/приложение) → доска
   (ошибки игрока, затем кубики росчерками для каждого продукта) → раковина (остудить) →
   миска (добавки, проба, перемешивание по кругу) → «Завершить день» → итог → перезагрузка.
5. **Снимки** — `production/qa/evidence/<день>_<экран>_<ширина>.png`, например
   `d1_board_carrot_cubes_1280.png`, `d1_phone_order_1440.png`. Обязательный набор:
   `menu, intro, kitchen, pause, recipe, stove_two, phone_home, phone_<app>, board_tutorial,
   board_<продукт>, board_<продукт>_cubes, sink_cool, bowl, bowl_mixing, olivier_done, result`.
6. **Перекрытия** — для каждой области интереса (продукт на доске, миска, кастрюли,
   героиня) взять сетку 5×5 точек через `view.localToScreen` и
   `document.elementFromPoint(x, y)`: точка закрыта, если элемент не `canvas#scene`
   или точка за кадром. Доля закрытых точек > 10 % — провал с именем перехватчика.
   Для панелей между собой: пересечение `getBoundingClientRect()` двух видимых
   панелей больше 8 px по обеим осям — провал (кроме модалки поверх затемнения).
   Перед каждым нажатием мыши на canvas проверять `elementFromPoint` в точке нажатия:
   любой перехватчик записывается.
7. **Ассеты видимы** — в обзоре кухни героиня и кот в кадре
   (`view.worldToScreen(...)` внутри 0–100 %), запросы `models/*.glb` без 404
   (`page.on('response')`), на снимке нет пустого места вместо модели.
8. **Устойчивость** — после серии ошибок (мимо, наискосок, клик без движения, перенос
   до разреза, горячий продукт) следующее верное действие обязано сработать.
9. **Сверка с чек-листом** — пройти разделы `visual-qa-checklist.md` по снимкам обоих
   разрешений; пункт отмечается только при наличии снимка или строки `OK`.
10. **Уборка** — `ps aux | grep "vite preview --port 4174"`, затем `kill <pid>` своего
    сервера. Чужие процессы не трогать, `kill -9` не применять.

## Что считается провалом

- любая ошибка в консоли или `pageerror`;
- отладочная панель или счётчики в обычном режиме;
- продукт/миска/кастрюля закрыты интерфейсом больше чем на 10 %;
- панель выходит за край окна или две панели пересекаются;
- игровое действие мышью не сработало и потребовался обход через `session`
  (это баг интерфейса, даже если сценарий дошёл до конца);
- после ошибки игрока игра не принимает верное действие (зависание);
- снимок показывает дубль продукта, пустую модель или квадрат вместо продукта;
- день 1 не завершается или прогресс не сохраняется после перезагрузки.

Падение шага из-за того, что кнопку **прямо сейчас** переделывают (сменился `data-act`),
отмечается как «не проверено — интерфейс в работе», а не как OK.

## Как отчитываться

Вердикт — одно из трёх, старшинство `FAIL` > `NOT ASSESSED` > `PASS`:
`FAIL` — есть хоть один провал; `NOT ASSESSED` — провалов нет, но часть не прогнана
(одно разрешение, раздел чек-листа, браузер не запустился) — назвать, что и почему;
`PASS` — всё прогнано на обоих разрешениях и чисто. Пропущенный шаг называется в отчёте
по имени: молчаливый пропуск выглядит как успех.

Ответ родителю (файл-отчёт не писать):

```
Вердикт: FAIL | NOT ASSESSED (<что не прогнано>) | PASS
Сборка: <commit> · разрешения: 1280×720, 1440×900
e2e день 1: N OK / M FAIL на каждом разрешении
FAIL: <имя проверки> — <деталь> — снимок production/qa/evidence/<файл>
Обход через session: <список или «нет»>
Перекрытия: <элемент → область, %>
Консоль: <число ошибок, первые 3>
Чек-лист: отмечено X из Y; не проверено — <разделы и причина>
```

Найденные дефекты оформлять через `/bug-report` (серьёзность S1–S4: зависание или
невозможность завершить день — S1; перекрытие продукта, нерабочий жест — S2;
обрезанный текст, мелкая накладка — S3/S4).
