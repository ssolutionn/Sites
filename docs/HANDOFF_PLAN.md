# План работ 0.8 — для исполнителя (Sonnet) и владельца

Составлен 2026-10-10 по версии 0.7.1, по внешнему ревью ChatGPT и по `docs/IMPROVEMENTS.md`.
Задачи написаны так, чтобы их могла делать модель дешевле Opus: у каждой есть файлы, шаги, тесты и признак «готово».
Где нужна модель сильнее или решение владельца — так и написано.

## 0. Для владельца: как этим пользоваться

**Какая модель что делает**

| Работа | Модель |
|---|---|
| Задача из этого плана по готовой карточке: логика, сохранения, тесты, CI, интерфейс | **Sonnet** |
| Новый жест по спецификации (логика + 3D + звук) | **Sonnet**, ревью Opus после блока |
| Сложная 3D-часть: нож и куски (`raster-cut.js`, `cutboard.js`), шейдеры, производительность | Sonnet для простого, **Opus** для этих файлов |
| Развилки, разбор твоих правок после прохождения, новый план, ревью блока | **Opus** |
| Тексты: уроки, подсказки, лента | **Sonnet** (навык `recipe-design`) |
| README, переименования, прогон тестов, сборка пакета для ревью | **Haiku** или Sonnet |

Haiku для разработки этой игры не советую: проект большой (≈19 тыс. строк), почти каждая правка задевает логику,
сцену и интерфейс сразу, а ошибка в жесте видна только при игре. Haiku годится для механической работы.

По ценам API (за миллион токенов, вход/выход): Opus 5.5 — $4 / $20, Sonnet 5.5 — $2 / $10, Haiku 5.5 — $0,10 / $0,50.
Sonnet вдвое дешевле Opus за токен. В подписке это значит, что лимит расходуется медленнее. Но дешевле выходит
только тогда, когда задаче не нужно три захода вместо одного: поэтому карточки ниже такие подробные.

**Как запускать сессию исполнителя** — новая сессия Claude Code в этом репозитории, модель Sonnet
(в Claude Code — команда `/model` или выбор модели при создании сессии), первым сообщением:

```text
Ты продолжаешь разработку «Симулятора новогодней суеты». Работай в ветке claude/technical-specification-mx99wl.
Прочитай docs/HANDOFF_PLAN.md: раздел 1 (правила) и задачу <A1>. Сделай только эту задачу.
Сначала проверь по коду, что описание в карточке всё ещё верно; если нет — остановись и напиши, что изменилось.
Тест, который ловит проблему, должен сначала упасть на старом коде. В конце — npm test, коммит, push
и отчёт по шаблону из раздела 8.
```

Маленькие задачи одного блока (например, A2 + A8) можно давать одной сессией. Большие — по одной.

**Контрольные точки с Opus** — после блока A, после блока B и перед релиз-кандидатом. Запрос для такой сессии —
в разделе 8.

**Что решаешь ты** — помечено значком ⚑. Пока решения нет, исполнитель делает вариант «по умолчанию»,
если он указан, иначе пропускает задачу.

## 1. Правила для исполнителя (читать каждый раз)

1. Сначала `CLAUDE.md` (подгружается сам) и `docs/CODE_TOUR.md` — карта кода. Механики «руками» — навык `game-feel`
   и `design/gdd/interaction-spec.md`; интерфейс — навык `game-ui-ux`; звук — `audio-feedback`; тексты о еде — `recipe-design`.
2. **Решения владельца не трогать** (CODE_TOUR, раздел 6): нож по сетке, A/D, рубка, «посолить → перемешать → попробовать»,
   «досыпать картошки», солёный и свежий огурец, чистка, кран, канапе, «Андрей», публичные ссылки только нейтральные.
3. Логика — в `KitchenSession` (`src/campaign/`), без DOM и three.js. View и UI только читают состояние и получают события.
   **Все игровые числа — в `src/campaign/data.js`.**
4. **Тест вперёд.** Для бага — регрессионный тест, который падает на старом коде (запусти и покажи это), потом исправление.
   Тесты — `tests/*.test.js` (`node:test`), помощники игрока — `tests/helpers-campaign.js`.
5. **Изменил то, что видно игроку, — сделай снимок** в `production/qa/evidence/` (сценарии `scripts/*-shots.mjs`).
   Playwright: `PW=/opt/node-tools/node_modules/playwright/index.mjs`, сервер: `npx vite build && npx vite preview --port 4173 --strictPort`
   (в фоне). Рендер программный, 1–3 кадра/с: кликай через DOM и жди `window.__sueta.sv.camT >= 1` после смены станции.
6. Перед коммитом: `npm test` зелёный. Для правок дня 1 — ещё `node scripts/campaign-e2e.mjs http://localhost:4173/ d1`.
7. Коммит — Conventional Commits на русском, в теле `Task: <id>`, в конце строки соавторства из системной подсказки.
   Push: `git push -u origin claude/technical-specification-mx99wl`. PR не создавать.
8. Запрещено: `rm -rf`, `git push --force`, `git reset --hard`, `git clean -f`, `sudo`, читать или писать `.env*`.
9. **Не придумывай дизайн.** Если карточка не отвечает на вопрос «как должно быть» — остановись и спроси владельца
   одним коротким вопросом с вариантами.
10. Обнови `CHANGELOG.md` (раздел следующей версии) и, если менял поведение, `docs/CODE_TOUR.md`.

## 3. Блок A — сохранения и режимы (делать первым)

### A1. Миграции сохранений вместо сброса
- **Модель:** Sonnet · **Размер:** S–M · **Файлы:** `src/campaign/save.js`, `src/main.js`, `src/ui/campaign-ui.js`, новый `tests/save-v08.test.js`
- **Сейчас:** `parseSave` при `data.version !== CAMPAIGN.saveVersion` возвращает `emptySave()` со статусом `reset`.
- **Сделать:**
  1. `export const MIGRATIONS = {}` — ключ «из какой версии», значение `(data) => data` следующей версии.
     `parseSave(raw, { version = CAMPAIGN.saveVersion, migrations = MIGRATIONS } = {})` — параметры нужны тестам.
  2. Версия старее текущей → применить миграции по цепочке, статус `migrated`. Шага в цепочке нет → статус `reset`.
  3. Версия новее текущей (сохранение от более новой игры) → статус `newer`, данные не трогать.
  4. В `SaveStore`: если сырые данные были, а статус не `ok`/`empty`, сначала положить их как есть в ключ
     `${SAVE_KEY}.backup` (одна копия, перезаписывается). Для `newer` не писать в основной ключ, пока игрок
     не начал новую кампанию.
  5. В меню один раз показать: «Сохранение от другой версии игры — копия сохранена» (`reset`, `newer`).
- **Тесты:** цепочка 1→2→3 на выдуманных миграциях: завершённый день остаётся завершённым, медали и баллы на месте;
  нет шага → `reset` и копия записана; битый JSON → копия записана; версия новее → копия есть, основной ключ не перезаписан;
  текущая версия → `ok`, копии нет. Хранилище — простой объект `{ getItem, setItem }`.
- **Готово:** новые тесты падают на старом коде и проходят на новом; `npm test` зелёный.

### A2. Честная запись сохранения
- **Модель:** Sonnet · **Размер:** S · **Файлы:** `src/campaign/save.js`, `src/main.js`, тест в `tests/save-v08.test.js`
- **Сделать:** `write()` возвращает `false`, если хранилища нет. Свойство `available`. В `main.js`: если хранилища нет —
  один раз тост «Прогресс не сохраняется: браузер запретил хранилище»; если `write()` вернул `false` в итоге дня —
  тост «Не удалось сохранить результат дня».
- **Тесты:** `new SaveStore(null).write() === false`; хранилище, у которого `setItem` бросает исключение, → `false`;
  обычное → `true`.

### A3. Испытания и практика не трогают кампанию
- **Модель:** Sonnet · **Размер:** S–M · **Файлы:** `src/main.js` (`enterKitchen`, `dispatch`, `startDay`), `src/campaign/session.js`,
  `src/campaign/st-phone.js` (`buyDecor`), новый `src/campaign/persist.js`, новый `tests/persist.test.js`
- **Правило (по умолчанию, ⚑ можно поменять):** испытание — отдельный режим. Оно не пишет `inProgress`, не меняет баллы
  и декор кампании, результат идёт только в `save.challenges`. В испытании и практике покупка декора недоступна:
  `buyDecor` возвращает `false` с подсказкой «Декор покупается в кампании».
- **Сделать:**
  1. Сессия знает режим: `new KitchenSession({ …, challenge: true })` из `startDay`, если передан `ch`.
  2. Вынести решения о записи в чистые функции `src/campaign/persist.js`, например
     `markInProgress(save, { dayId, practice, challenge })` и `applyDecorPurchase(save, { id, price, practice, challenge })`.
     `main.js` только вызывает их и `save.write()`. Так это можно проверить тестами без браузера.
- **Тесты:** вход в испытание не записывает `inProgress`; покупка в испытании и практике не меняет `save.bonus`/`save.decor`;
  обычный день записывает `inProgress`.

### A4. Баллы недоигранного дня не попадают в сохранение
